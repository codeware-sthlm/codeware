### Findings worth keeping

- **The success badge failed contrast.** `--success-subtle` (green-700) on a 10% green
  fill measures 4.33:1 at 12px, under axe's 4.5:1. Caught by the Storybook a11y suite,
  not by eye. The badge is now tinted on its border only; the same green clears the
  threshold against the card's own background. Worth remembering before tinting any
  other `*-subtle` token as a fill.
- **`Stored<T>` was too shallow.** Payload widens _every_ level to nullable-optional, so
  the first array-of-objects field added to `CertificateState` broke assignment in both
  certificate endpoints. It now widens array elements too, leaving arrays of primitives
  (`validationErrors`) alone.
- **`node:dns` cannot live behind the domains barrel.** The panel is a client
  component that imports `@codeware/app-cms/feature/domains` for values, so everything
  the barrel re-exports lands in the admin's browser bundle — and a `node:` builtin
  fails it outright. `nx run cms:build` passed anyway; only turbopack's dev bundler
  reported it. The querying half now sits behind a `@codeware/app-cms/feature/domains/server`
  entry that only the endpoint imports, with the types and pure rules staying in the
  barrel. **`cms:build` is not a sufficient gate for this class of mistake — `nx dev cms`
  is.**
- **DoH was rejected for a reason that no longer applies.** It could not have queried
  authoritative nameservers — but that half was cut, so the choice of `node:dns` now
  rests only on it being the smaller dependency. If UDP/53 turns out to be blocked on
  Fly, switching the three public resolvers to DoH is a contained change.

## The shape of it

The Platform tab is a **classic admin dashboard**: a grid of status widgets whose scope is
cross-tenant _including_ the platform itself. Not a table of rows.

Each widget is a card with a large status icon, a count or headline value, and one line naming
the worst thing found. The normal case is a big green shield and nothing to read. When
something is off, the _same place_ says so — one glance, one location, no drilling to find out
that everything is fine.

Clicking a widget opens a `Sheet` with per-item detail. Not every widget needs one.

**Three widgets ship together**, so the tab arrives as a dashboard rather than a lonely card,
and they fill the `sm:grid-cols-2 xl:grid-cols-3` grid exactly:

1. **Domains & certificates** — the one that motivated the ticket.
2. **Integrations** — email / Sentry / S3, all resolved at boot.
3. **Environment & build** — version, sha, deploy env, app mode.

Widgets 2 and 3 read entirely from the already-parsed env object. **No new I/O for either**,
which is what makes them worth adding now rather than later.

## Why this order

**COD-442 first.** It restructures the card into `Card`/`Badge`/`Alert` and yields an
extractable status pill the domains sheet reuses. Running it after the others means they add
raw-Tailwind that 442 then rewrites.

**COD-446 second**, domains widget before the other two: it is the hard one and it settles the
pattern the other two follow.

**COD-439 third.** Small and additive — its detail lands in the domains sheet from step 4.

**COD-437 last, and optional.** See step 9.

## What was verified

Read directly on `main` before planning:

- **`issued` is not fetched today.** `CERTIFICATE_FIELDS`
  (`packages/fly-node/src/lib/fly-api.class.ts:480-504`) lists 20 fields; `issued` is not among
  them. `certificateAuthority` **is** (line 489), so the CA needs no new field — only the
  `issued` connection paired with it. This makes step 7 a change to a **published package**.
- **Storing issued certs is a schema change.** The `certificate` group
  (`domains-field.ts:93-105`) has nine fixed subfields; adding issuance rows means a migration
  in `apps/cms/src/migrations` (latest: `20260817_212656_cod_436_platform_settings.ts`).
- **…and storing them is required, not optional.** The panel renders stored state and never
  calls Fly on load (`DomainsPanel.client.tsx` docblock). Issued certs held only in browser
  state would vanish on reload — the exact failure COD-438 existed to fix.
- **Home is tenant-scoped.** `AdminDashboardView.tsx:70` funnels every query through
  `getTenantWhere(user)`. The Platform tab's scope is the opposite by design.
- **Tab preferences are validated against a static list.** `dashboard-preferences.ts:9-14` —
  `DASHBOARD_TABS` is `['home', 'content']`, membership-checked with no notion of role;
  `AdminDashboardView.tsx:107` seeds from it server-side. See step 3.
- **Certificate reads are broadly permitted; writes are not.** `tenants.read` is
  `restrictToTenantInTenantMode`, which returns `true` for any authenticated user in host mode,
  and `platform-settings.read` is `authenticatedAccess`. Only the _endpoints_ gate on
  `hasRole(user, 'system-user')`. The tab must apply its own role gate — inheriting collection
  read access would expose it to editors.
- **`Sheet` exists in shadcn** (`libs/shared/ui/shadcn/src/lib/components/sheet.tsx`).
- **There is no warning tone.** The theme sets define `--success-subtle` and
  `--destructive-subtle` only (`shadcn/theme-light.css:35-37` and its dark twin).
  `--cdwr-warning` exists solely in `payload-retheme.css`, which is one-directional and not a
  shadcn token source. See step 2.
- **Integrations resolve to configured-or-`undefined` at boot.**
  `env.schema.ts:252-297` — `EMAIL` becomes `{sendgrid}` | `{smtp}` | `{ethereal}` |
  `undefined`, `SENTRY` and `S3_STORAGE` (line 240) become an object or `undefined`. Free to
  read; the discrimination step 5 needs is already done.
- **`getAppInfo(env)` already assembles the build metadata** (`apps/cms/src/app-info.ts`) for
  the About dialog — name, version, sha, deploy env, build time. Step 6 reuses it as-is.
- **`getEnv()` revalidates on every call** (COD-421). Call it **once** in the dashboard view and
  pass the parsed env down, exactly as `app-info.ts` documents.
- **No DNS resolution anywhere in the repo.** No `node:dns` import in `libs`, `apps` or
  `packages`. Step 9 is greenfield.

## Widgets considered and deferred

Recorded so they are not re-litigated:

- **Fly connectivity / machine status** (COD-443) — needs Fly calls on load, which breaks the
  rule the whole design rests on. A later widget, fed by something cached or lazy.
- **Fly/Infisical credential presence** — `getFlyApi()` returning `null` would answer it, but it
  reads Infisical over the network. Same objection. Could load lazily inside the Integrations
  sheet if wanted.
- **Pending migrations** — a deploy-time concern; Payload does not expose it cheaply at runtime.
- **Query profiler** (`endpoints/perf-stats.ts`) — opt-in dev debugging tool, not a status.
- **Workspace/user counts** — free from the DB, but no non-invented "fishy" rule was found.
  Counts alone do not earn a widget slot.

## Steps

### Step 1 — COD-442: shadcn adoption

Work through each candidate; keep a custom build only with a stated reason.

- `DomainCard` outer container (`domain-card.tsx:122`) → `Card` / `CardContent`.
- The `Status` pill (`domain-card.tsx:261-296`) → `Badge`, **extracted as its own exported
  component** — steps 4 and 8 reuse it. Compare against
  `libs/app-cms/ui/dashboard/src/lib/status-badge.tsx`, but note that one deliberately uses a
  single style for all values; here the colour _is_ the signal, so it is a reference only.
- `pausedMessage` (`domain-card.tsx:138`) → `Alert` + `AlertDescription`, destructive variant.
- `DnsRecord` outer panel (`dns-record.tsx:86`) → judgement call. A `Card` nested in a `Card`
  may read worse than the current muted block. Check both.
- `Record` rows (`dns-record.tsx:167`) → likely stay custom; the copy-button positioning and
  `break-all` mono layout have no shadcn equivalent.

### Step 2 — `--warning-subtle` theme token

The widgets need three tones, and "pending" is not destructive-red. Add `--warning-subtle`
alongside the existing pair, following its exact pattern (amber-400 dark / amber-700 light,
with the same explanatory comment).

Eight files: `shadcn`, `payload-admin`, `codeware`, `spotlight` × light/dark under
`libs/shared/theme/src/lib/`. Theme files are the shadcn token source of truth, so this is the
right layer — do **not** reach for `--cdwr-warning` from `payload-retheme.css`, which flows the
other way.

### Step 3 — COD-446: `StatusWidget` shell + Platform tab

**Widget shell** in `libs/app-cms/ui/dashboard` — dashboard vocabulary, reused by all three
widgets and whatever follows. Presentational and hook-free like the rest of that lib:

```ts
type StatusWidgetProps = {
  icon: IconComponent;
  tone: 'ok' | 'warning' | 'error' | 'neutral';
  title: string; // "Domains & certificates"
  metric: string; // "8 domains"
  detail: string; // "All certificates active"
  onOpen?: () => void; // click → sheet; omit for a widget with no detail view
};
```

`tone` drives the icon colour only — the card itself stays neutral, so a grid of widgets reads
as a grid rather than a traffic light.

**Tab wiring:**

- Add `'platform'` to `DashboardTab` (`libs/app-cms/ui/dashboard/src/lib/types.ts`).
- Trigger + content in `AdminDashboard.client.tsx`, conditional on role.
- Content is a responsive grid, same idiom as the Home task grid
  (`grid gap-4 sm:grid-cols-2 xl:grid-cols-3`).
- **Role-aware seeding.** Keep `isDashboardTab` a pure shape check; apply the role gate where
  `resolveActiveTab` runs (`AdminDashboardView.tsx:107`), so a demoted user whose stored
  preference is `platform` falls back to `home`. Without this they get a `Tabs` value with no
  matching trigger, which renders a blank pane silently.
- Pass the role decision down as a prop; do not re-derive it client-side.
- Call `getEnv()` **once** here and pass the parsed env to steps 5 and 6.

### Step 4 — COD-446: domains widget + detail sheet

**Server.** Read all tenants' `domains` plus the `platform-settings` singleton, stored
`certificate` groups only. **No Fly calls.** Flatten to one row per domain carrying hostname,
app, status, `checkedAt` and the owning document's admin URL.

**Aggregate rule** — worst wins, from stored state alone:

| Tone      | When                                                              |
| --------- | ----------------------------------------------------------------- |
| `error`   | any certificate paused (rate-limited), or active with open issues |
| `warning` | any pending, or any domain with no certificate requested          |
| `ok`      | every domain has an active certificate with no open issues        |
| `neutral` | no domains configured at all                                      |

The detail line names the worst finding with its count — "2 pending", "1 rate limited" — not a
generic "needs attention". `ok` reads "All certificates active".

**Sheet.** shadcn `Sheet`, one row per domain, reusing step 1's status pill; each row links to
the owning document's domains panel. Read-only — the panel owns the actions. Sort worst-first
so the reason the widget is amber is the first row.

`DomainStatusRow` goes in `libs/app-cms/ui/domains`, next to `DomainCard` — domain vocabulary,
not dashboard vocabulary. Export it for the dashboard to consume.

### Step 5 — COD-446: integrations widget + sheet

Reads the parsed env from step 3. No I/O.

| Tone      | When                                                                         |
| --------- | ---------------------------------------------------------------------------- |
| `error`   | `DEPLOY_ENV` is `production` and `EMAIL` is `undefined` — mail goes nowhere  |
| `error`   | `DEPLOY_ENV` is `production` and `EMAIL` resolves to `ethereal` or a catcher |
| `warning` | `production` with no `SENTRY`, or no `S3_STORAGE`                            |
| `ok`      | every integration resolved to something appropriate for the deploy env       |
| `neutral` | `development` — a catcher or Ethereal is correct there, not a finding        |

"Production is quietly posting password resets into a throwaway inbox" is the case this exists
to catch; nothing surfaces it today.

Sheet lists each integration with its resolved transport — `EMAIL` by its discriminant
(`sendgrid` / `smtp` / `ethereal` / not configured), `SENTRY` and `S3_STORAGE` as configured or
not. **Never render secret values** — the transport name and host at most, no keys, no
passwords.

### Step 6 — COD-446: environment & build widget

`getAppInfo(env)` gives name, version, sha, deploy env and build time; add `env.APP_MODE.type`
(`host` / `tenant`). Metric is the version; detail is deploy env + mode.

Mostly informational, so `neutral` is the normal tone. One real finding worth flagging:
`warning` when `DEPLOY_ENV` is `production` and `sha` or `buildTime` is empty — that means an
unstamped build is running in production and nothing can say which commit it is.

No sheet — the About dialog already exists for the full detail. Consider making the widget open
it via `OPEN_ABOUT_EVENT` (`AboutDialogHost.client.tsx`) rather than building anything new.

### Step 7 — COD-439: data path

Deliberately small; the user's framing is that per-cert detail is not the valuable part.

1. **fly-node.** Add to `CERTIFICATE_FIELDS`:

   ```graphql
   issued(first: 10) { nodes { id type expiresAt hostname } }
   ```

   Extend the zod schema in `packages/fly-node/src/lib/schemas/certificate.schema.ts` and
   update the fixture `__fixtures__/fly-api/certificate.json` — it is registered for schema
   testing in `schemas.spec.ts:53`, so a new field without a fixture update fails the suite.
   `fly-node` is **published**: additive, non-breaking, but it needs a version bump at release.

2. **Stored state.** Add to `CertificateState` in `certificate-state.ts`, e.g.
   `issuedCertificates: Array<{ type: string; expiresAt: string }> | null`, and pick up
   `certificateAuthority`, which `toCertificateState` currently drops. `applyCertificateState`
   writes the whole state object, so it should need no change — confirm.

3. **Field + migration.** Add the subfield to the `certificate` group
   (`domains-field.ts:93-105`) — an array, so its own table. Generate the migration and confirm
   the **down** migration drops in the right order: COD-436 hit a real bug where an FK had to
   be dropped before the table it cascades to.

> If this branch gets a preview deploy and the migration is then regenerated, that PR's preview
> DB must be dropped by hand — `test-migrate` does not catch it.

### Step 8 — COD-439: certificate rows in the domains sheet

Type and expiry on one line, CA as muted secondary text — reusing the `Record`-row idiom from
`dns-record.tsx:152-167`. No shadcn `table`: there is none in the workspace, and two rows whose
expiry and CA are identical do not earn a header row.

Render only when `issuedCertificates` is non-empty — certificates stored before the migration
have none and must not produce an empty box.

Once expiry exists, extend step 4's aggregate rule with `warning` for anything expiring inside
14 days. Derive "days until expiry" in one shared helper.

### Step 9 — COD-437: pragmatic resolver comparison (opt-out gate)

**Scope cut, per the user: this must not become a technical monster, and dropping it entirely
is an acceptable outcome.**

What the ticket describes in full — NS lookup, resolving each nameserver to an IP, querying
each authoritative server, merging three answer sources — is the expensive half and the reason
this looked like a monster. Cut it.

The pragmatic version keeps the diagnostic value that motivated the ticket. The original
incident was a stale CNAME cached by the operator's own router while every independent resolver
already had the right answer. Three public resolvers agreeing is _already_ that signal; the
authoritative check only confirms what they said.

Ship this and nothing more:

```ts
const resolver = new Resolver({ timeout: 2000, tries: 1 });
resolver.setServers(['1.1.1.1']); // and 8.8.8.8, 9.9.9.9
await resolver.resolveCname(hostname);
```

- Three public resolvers, the record the panel already suggests, in parallel, short timeout.
- `resolveSoa()` for `minttl` — the negative-cache TTL, one extra call, no parsing.
- Verdict: all agree / they disagree. Copy names the difference between "not propagated yet"
  and "your own resolver is stale", with the TTL as the concrete number.
- Behind its own button in the panel, not part of the normal check.

Endpoint alongside the certificate ones, gated on `system-user` exactly as
`tenant-domain-certificate.ts:57` does. Keep it separate from the existing check endpoint: it
has a longer latency and a different failure profile, and coupling them would make a slow
resolver look like a broken Fly check.

**Risk:** needs outbound UDP/53 from the Fly machine. Expected to work, unverified. A resolver
that times out reports "no answer from this resolver" — never an error that takes the panel
down, never a hang without a timeout.

**Opt-out gate:** if step 9 exceeds roughly a day, or UDP/53 turns out to be blocked, drop it
and ship steps 1–8. Note the outcome on COD-437 and leave it open.
